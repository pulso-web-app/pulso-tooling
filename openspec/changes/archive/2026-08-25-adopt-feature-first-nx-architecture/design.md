## Context

See `proposal.md` for motivation. The parent workspace deliberately coordinates three independent Angular/Nx repositories through public npm scripts. The existing artifact generator only accepts `apps/<app>/src/app`, while feature code will move to tagged projects below `libs/`.

## Goals / Non-Goals

**Goals:**

- Preserve independent repositories while giving every application repository a meaningful internal Nx graph.
- Keep current component, service, guard, directive, pipe, interceptor, and resolver workflows usable after code moves into libraries.
- Make feature-first ownership and the distinction between repository, MFE, and library boundaries discoverable to humans and agents.
- Keep generator path validation deterministic and covered by `node:test`.

**Non-Goals:**

- Create a parent Nx or npm workspace.
- Generate new MFEs or speculative domain layers.
- centralize application dependencies, caches, CI, or deploys.
- Change runtime federation contracts.

## Decisions

### Keep cross-repository coordination outside Nx

`pulso-tooling` continues invoking public npm scripts in each repository. Nx owns the graph and task execution inside one domain repository; tooling owns setup and integrated developer experience across repository boundaries. A parent monorepo was rejected because it would remove the ownership and deployment model this portfolio intentionally demonstrates.

### Recognize explicit Angular source roots

Artifact generation accepts the application source root and any `libs/**/src/lib` directory inside the selected known workspace. It does not accept arbitrary workspace directories. This supports feature libraries without weakening the existing absolute-path, traversal, selected-resource, and local-binary protections.

### Keep artifact generation separate from project architecture

The current artifact allowlist and Nx Angular generators remain stable. Architectural project creation is documented as a deliberate operation because a new library requires an ownership decision, tags, and dependency constraints; it is not inferred from an arbitrary component request.

### Synchronize guidance through canonical Skills

Canonical `pulso-*` Skills and authoritative `AGENTS.md` files describe feature-first placement. Existing mirrors remain generated by `agent:sync`; OpenSpec-managed integrations remain untouched.

## Risks / Trade-offs

- [Broader accepted path accidentally permits root-level generation] -> Require a target to be inside either the exact app source root or a path matching `libs/<segments>/src/lib` and cover rejection cases.
- [Documentation drifts across four repositories] -> Use one change ID, update canonical instructions, synchronize mirrors, and run `agent:check` plus Markdown validation.
- [Internal Nx projects are mistaken for deployable MFEs] -> Document the three boundary levels explicitly and preserve the existing federation topology.

## Migration Plan

1. Record application-owned deltas under the shared change ID.
2. Add meaningful libraries, tags, boundaries, and project-aware scripts in each application repository.
3. Extend tooling source-root resolution and tests, then update workspace documentation and agent guidance.
4. Validate each app, validate the aggregate tooling check, archive app changes, and archive the tooling umbrella last.

Rollback is repository-local: restore application source paths and aliases, then restore tooling source-root validation. No data, hosting, or runtime-contract migration is required.
